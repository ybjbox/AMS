## 一、当前系统能力盘点（2026-09-22 实测）

前端 13 个页面（`src/config/routes.ts`）：控制台、员工管理、部门管理、考勤管理、合同管理、宴会排座、
会议台卡、常用文件、待办事项、审批中心、微信通知、业务单据、系统设置。
服务端 22 个路由（`server.ts:137-158`），数据落在单文件 SQLite（`node:sqlite`，WAL），schema 版本 v13。

### 1.2 仍然没有的东西（别自欺）

- **通用审批引擎**：四类流程写死在 `approvalsDb`，新增一种单据要改代码。没有 `approval_templates`、条件分支、加签/转交、抄送。
- **员工自助门户**：没有 `/portal` 与按角色分流的精简导航。EMPLOYEE 现在能自助提交补卡/请假、看待办与通知、改自己的资料与头像，但看不到"我的考勤/我的假期余额/我的合同"。
- **资产、会议室、报修服务台、访客、车辆**：一个都没有（代码里搜不到 `assets` / `meeting_rooms` / `tickets`）。
- **考勤实时性**：数据靠 Excel 导入，没有打卡机/企微同步，异常分析永远是"事后补算"。
- **深度分析**：个人异常画像、部门健康度打分、离职风险信号都没有，只有聚合计数。

### 1.3 工程健康度（支撑"敢用"的那部分）

`npx vitest run` 48 文件 / 256 测试；Playwright e2e 42 例（含权限矩阵、四类审批闭环、导入异步链路、手动排座）；
GitHub Actions 两个 job（verify：typecheck / lint / 单测 / 11 个服务端回归脚本 / 生产构建；e2e）全绿；
`eslint .` 0 error；仓库内不再保存任何明文凭据（e2e 走 `.env.local`，CI 每次现生成）。

## 二、行业调研结论仍然成立的部分

7 月版四条主线，除第一条外都仍然适用：

1. ~~AI 原生重构~~ → 补充观察：AI 助手做完了"能问"，但**没有接进业务动作**（不能"帮我提个下周一的假"），
   在这套系统里 AI 更像独立功能页，而不是贯穿流程的能力。
2. **一体化数据互通**：已经吃到第一波红利（审批 ↔ 打卡 ↔ 调休额度 ↔ 考勤异常互相写回），下一步是"考勤采集即数据源"。
3. **合规与溯源**：审计、脱敏、权限、备份四件套已到位，剩下的是水印/导出留痕与等保类文档化。
4. **员工自助 + 主动预警**：预警这半已落地（合同/试用期），自助那半只做了"发起"，没做"查看自己"。

## 三、改进建议（按 ROI 重排）

### 🥇 第一梯队

#### N1. 考勤数据源接入（企业微信打卡同步）⭐⭐⭐⭐⭐
**为什么排第一**：现在所有考勤分析、异常申诉、调休额度都建立在"HR 手工导 Excel"上，这是这套系统最大的失真来源。
三个决策已于 2026-09-23 定下（见 `docs/WECOM-ATTENDANCE-INTEGRATION.md` 第五节），**P0+P1 链路已落地**：
凭据掩码配置 / token 缓存 / 29 天分段 + 100 人分批 / 敏感字段在客户端边界即丢弃 / userid↔工号人工认领 /
幂等增量落库（`punch_records.source`）/ 干跑预览 / 定时调度（默认关）。回归 `server/tests/wecom-sync.test.ts`。
**还剩一件事**：真实凭据 + 固定公网 IP（可信 IP 是硬门槛，配好后在设置页填 CorpID/Secret 即可，代码不用再动）。
判定层已按用户口径重做：**部门工作时段 + 按打卡时间自动对班**（`server/shiftMatch.ts` / `shiftRulesDb.ts`，
考勤页新增「部门时段」，异常分析返回 coverage 说明多少人日未被判定），不再要求 HR 逐日排班。
2026-09-24 补上**三班倒**：判定单位从"日历日"改成**班次实例**（`buildShiftInstances`），归属日 = 首卡那天，
末卡可以跨到次日。凌晨 00:0x 那张卡按"是否已有首卡"归属——中班（16:00–00:00）的人它是下班卡，
还没上班的夜班的人它是本班上班卡；24 点班与 20:00–04:00 这类真跨日班在时段配置里直接可填（界面标「次日」）。

#### N2. 审批流：已按「纯重构」收口，模板引擎裁定不做
原设想是把四类流程抽象成 `approval_templates`（表单 schema + 节点 JSON）+ `approval_instances` / `approval_tasks`，
支持条件分支、加签/转交、抄送。**2026-09-24 裁定：纯重构，不加类型**——自用系统里没有"等着上的新审批类型"，
模板引擎换来的是配置能力而不是用户价值；多级会签/加签/转交/抄送此前也已裁定不做（ROI 低）。

实际落地的形态（`server/approvalTypes.ts`，2026-09-24）：
- 五类审批的差异（校验与字段归一化、审批门槛、给申请人的文案、列表标题与摘要）收进**一张类型规格表**，
  取代原先 110 行五分支提交链 + 两层三元式文案 + `decideApproval` 里的 if 链；
- 通过后的领域动作改成 `Record<ApprovalKind, fn | null>` 显式穷举 —— 新增类型时必须当场表态"通过后做什么"，
  不再出现"加了类型但通过后静默什么都不做"；
- 回归 `server/tests/approval-types.test.ts` 把每条错误文案、每条通知文案、每个归一化结果按重构前字面量钉住。

若将来真要加类型，剩下的成本是：规格表加一条 + （如有台账）领域动作加一条 + 表单页加一段字段。

#### N3. 员工自助门户 `/portal` ⭐⭐⭐⭐
按 `systemRole` 分流：EMPLOYEE 进精简门户（我的档案只读+发起变更、我的打卡与异常、我的假期与调休余额、
我的合同、我的工位），HR/ADMIN 保持现有后台。数据端点大多已存在，缺的是**视图与权限收口的最后一公里**。

### 🥈 第二梯队

#### N4. 数据驾驶舱升级 ⭐⭐⭐⭐
在 `/api/stats` 两组端点之上补：异常趋势（部门 × 月份红黄绿）、个人画像（"近 30 天迟到 8 次，环比 +60%"）、
加班强度与疲劳预警、合同风险日历。数据都在库里，缺的是聚合与呈现。

#### N5. AI 从"能问"到"能办" ⭐⭐⭐
阶段二：自然语言 → 发起审批单（走 `POST /approvals`，类型规格表已把"每类要哪些字段"收在一处）；阶段三：每周一自动汇总"人事异动 + 考勤概览"推送给 HR。
**不依赖模板引擎**：类型规格表就是 AI 代办需要的程序化入口。

#### N6. 离职风险与组织效能诊断 ⭐⭐
司龄区间 + 近 3 月异常率变化 + 无晋升记录 + 加班强度骤降，用规则打分而非黑盒模型，可解释优先。

### 🥉 第三梯队（原稿的行政闭环，按当前实际用法下调）

- **R3 资产管理（一物一码）** ⭐⭐⭐：仍是真空，领用/归还/报修/报废 + 离职时挡住未归还。
- **R4 会议室预定** ⭐⭐：时间轴防冲突 + 周期性预定；后期利用率分析可反哺工位规划。
- **R11 报修服务台** ⭐⭐：`tickets` + SLA；若走审批，需要在类型规格表里加一条（含"通过后做什么"的显式表态）。
- **R12 访客管理** ⭐：预约 → 二维码 → 核销 → 通知被访人。
- **R9 后半：动态水印与导出留痕** ⭐⭐：等保/ISO 场景需要时才升上来。

   ├─ R3 资产 → R4 会议室 → R11 报修 → R12 访客
   └─ R9 后半：水印与导出留痕

## 五、一句话结论

**AMS 已经不是"档案柜"了：审批、预警、审计、备份、单据、排座都通了，工程上也到了"敢给自己用"的状态。**
现在真正卡住它的是三件事——**考勤数据源（N1，链路已通、等凭据）、审批分支的可维护性（N2，已收口）、员工看不到自己的东西（N3）**。
把这三件做完，它才从"HR 的后台"变成"全公司的行政 OS"。
